# Repair planning based on diff.md

The common authority is maintained in the `ai-driven-infra-blueprints` repository. Present evidence-backed repair proposals and the plan selected by the human in chat to resolve differences, naming rule mismatches, and unconfirmed items recorded in `diff.md`.

## Plan mode and mandatory specifications

- **Plan mode is mandatory.** Confirm the actual collaboration mode. If it is not Plan mode, do not start target investigation; quote/link this skill requirement and ask the human to switch to Plan mode. Loading the skill or declaring that it is treated as Plan mode does not change the mode.
- Require the human to explicitly specify the environment name; limit one execution to one environment. If unspecified, multiple environments, or all environments are specified, use an ask question to request selection of one environment and do not start target investigation until answered. Do not infer it from paths, existing contracts, or the sole environment; do not automatically split into tasks per environment or execute sequentially.
- Require one or more service IDs explicitly specified by the human, or either `all service`/全サービス. If unspecified, confirm through an ask question; do not automatically expand to all services.
- Confirm the specified environment in `project.json` and service IDs in the selected target's model entries. Use the confirmed alias as target directory, or AWS account ID without an alias. If the environment has multiple targets and the target is unspecified, request selection through an ask question. If there is one target, that target may be used.
- Repair destinations are only within the specified environment. Refer to the comparison-source environment stated in diff.md only as read-only evidence necessary to confirm baseline values/resource correspondence; do not include it in repair destinations, change plans, or Validation scope. Distinguish comparison-source specification from specifying multiple repair environments.

## Read-only investigation

1. Read `AGENTS.md`, [issue-gate](../../../framework/rules/issue-gate.md), [Model authority](../../../framework/rules/model-information.md#model-authority), [Properties format](../../../framework/rules/model-information.md#properties-format), [Markdown structure](../../../framework/rules/detailed-design.md#markdown-structure) and target resource display/reference sections, [resource naming](../../../framework/rules/aws-resource-naming.md), [env-diff comparison](../env-diff/SKILL.md#comparison), and [AI organization](../env-diff/SKILL.md#ai-organization). Use env-diff as a reference for comparison/classification conventions; do not start execution/save tasks from this skill.
2. Read the selected target's `issues/<environment>/<target-directory>/diff.md` and `issues.md`. Ask about deficiencies if diff.md is absent, its comparison source/destination/target is unclear, or the specified environment differs from the repair destination. Do not infer comparison pairs/corresponding targets or automatically create/update diff.md.
3. For individual specifications, handle only the corresponding service items. For `all service`, target all services listed in the selected target's diff.md and show the actual service ID list. Do not expand to investigating/repairing unlisted services or treat absence from the report as a verified match. If no corresponding items exist, report that fact and finish.
4. Compare corresponding items with current `model/<environment>/<target-directory>/<service-id>.properties`. Read entry indexes/necessary parts as one logical service with the existing reader and treat `desired.*` as authoritative. Refer only to comparison-source pairs/targets explicitly stated in diff.md; distinguish stale reports, intentional environment differences, actual design differences, and unconfirmed/incomparable items. Do not infer resource correspondence or missing values.
5. Follow env-diff IMPORT exclusion, allowed environment differences, and naming/reference confirmation. Present proposals based on the comparison source while adjusting names/accounts/regions/reference targets to confirmed repair-destination values. Do not copy actual comparison-source names/IDs/ARNs unchanged. Include permission differences in repair proposals only after confirming the target resources and necessity.
6. For each item, confirm the target resource/property, current state/baseline, evidence files, recommended changes, impacts, and unconfirmed values. Read existing IaC read-only to distinguish whether model repair alone suffices or IaC repair is also needed. Do not retrieve current AWS values; treat the necessity of AWS reflection and actual state as unconfirmed.
7. Check unresolved issues in the latest issues.md. diff.md items themselves are not unresolved issues. For services with unresolved issues, do not proceed with ordinary design consultation; limit work to issue investigation and the repair scope explicitly specified by the human. If out-of-scope issues are blockers, indicate that their repair must precede this work; do not mix ordinary changes into a plan awaiting approval. Do not reuse save-only task exemptions for model/IaC repair.

## Present recommendations through ask questions

- After investigation, ask through `request_user_input` for each difference requiring a decision or each group with the same reason/repair policy. Ask 1–3 questions per call with 2–3 mutually distinguishable options per question. Put the recommendation first, append `(Recommended)` to its label, and briefly state changes, impact, and decision rationale in the description.
- Determine recommendations from the confirmed comparison baseline, naming rules, repair-destination use, and impacts. Use only options supported for that item, such as “align the repair-destination model with the baseline,” “retain as an environment difference,” or “defer until missing information is confirmed.” Do not re-ask policies already confirmed by the human.
- Use the same ask question format to confirm missing environments/services/targets or resource correspondence. Limit options to values confirmed in the current project/model; for more than 3 candidates or unconfirmed concrete values, show candidates/necessary information in the question body and accept free input. Do not invent nonexistent candidates.
- Putting a recommendation first is not an answer/approval. Keep decisions requiring answers undecided; do not treat no response/timeout as agreement to the recommendation. Subsequent independent read-only investigation may continue.
- Reflect answers in the plan. If an answer changes missing values or assumptions, reinvestigate only that scope. Do not treat answers selecting repair proposals as permission to execute repairs, AWS APIs, or deploy/apply.

## Presenting the plan and finishing

- Briefly show the specified environment/target/service, human-selected policy, repairs/confirmed values per resource/property, specific planned paths, dependencies/work order, necessary generation/validation, and undecided items in the final plan. Expand `all service` into actual service IDs; do not mix another environment into repair destinations.
- Present model repair, IaC repair, and AWS reflection as separate execution scopes. Model repair proposals must first change authoritative properties, generate Markdown/JSON per service with `sync-model.py --write`, and update only corresponding diff.md items after confirming repairs. When only the report is stale, propose updating diff.md after recomparison/classification; do not propose removing unrepaired differences from the report.
- Show confirmation methods and necessary human decisions for unconfirmed/incomparable items; do not treat them as repaired. Show procedures preserving out-of-scope service reports and unresolved issues. Include in the plan that future repository changes require the target task type's contract registration, specific file reservations, issue gate, and scoped local loop.
- This skill finishes with read-only planning. Do not register contracts, change diff.md/issues.md/model/generated artifacts/IaC, run generation commands, local loops, AWS APIs, deploy/apply, or scenarios, or create/execute another task. Handle plan saving/repair execution through a separate explicit human request; do not automatically execute even after leaving Plan mode.

Follow AGENTS.md “How to read required rules” for reading rules. Read [project-configuration](../../../framework/rules/project-configuration.md) for target determination and account/profile validation, and [issue-gate](../../../framework/rules/issue-gate.md) for stop and investigation/repair/save exception decisions. Do not read contract/local loop documents in this skill; finish with planning alone.
