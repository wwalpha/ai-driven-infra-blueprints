# ai-driven-infra-blueprints

A repository blueprint for humans, chatbots, and Codex to divide roles in designing, implementing, and validating AWS infrastructure without depending on a specific system architecture. The distributed state contains no project or IaC implementation.

## Initial setup

1. Pass `framework/prompts/codex/01_initialize.md` to Codex. Codex confirms the project, environment, alias only when needed, AWS account, region, and IaC engine needed for initialization in sequence, one question and answer at a time.
2. Answer only for targets whose required values are currently confirmed. Do not include uncreated environments/logical targets or those with unconfirmed required values in initialization scope.
3. Codex creates `project.json` and defined target paths from the answers and removes unselected IaC engine directories for all targets.
4. For previously unconfirmed targets, after required values are confirmed, pass `framework/prompts/codex/02_add-target.md` to Codex to add them.
5. Finish after initialization or migration task completion; do not automatically create or execute a design task.

`docs/system-overview.md` is optional background material independent of initialization. It may be filled in only to the extent known, before or after initialization. After initialization, the machine-readable source of truth for project topology is `project.json` generated by Codex. There is no procedure for humans to directly create/edit JSON. The blueprint does not fix environment names, environment counts, or AWS account counts.

Each `project.json` target may have an optional naming suffix. For example, specifying `"suffix": "aaaaaa"` for a target uses the selected environment/alias value for `{{suffix}}` in naming patterns. Values must be non-empty lower-kebab-case; only some targets may specify them. Omit `[-{{suffix}}]` together with its separator when unset; stop if mandatory `{{suffix}}` is unset. Do not change patterns without suffix or existing names. Confirm during initialization/target addition; add/change/remove it for existing targets through an explicitly specified migration task in Codex.

Each `project.json` target may have optional `awsProfile` and `awsExecutionAccountId`. Specify values confirmed during initialization/target addition; omit unnecessary fields. To register/change/remove execution account IDs for existing targets, request a migration task in Codex explicitly specifying the target and value.

```json
{
  "environment": "dev",
  "awsAccountId": "123456789012",
  "awsExecutionAccountId": "210987654321",
  "awsRegion": "ap-northeast-1",
  "iacEngine": "cloudformation",
  "awsProfile": "dev-admin"
}
```

When configured, preflight and the CloudFormation controller use it automatically; add `--profile` to direct AWS CLI calls too ([AWS CLI named profiles](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-files.html)). Explicitly specify the profile for SDKs; pass it to the target process's `AWS_PROFILE` for Terraform ([AWS provider authentication configuration](https://registry.terraform.io/providers/hashicorp/aws/latest/docs#authentication-and-configuration)). Without a configured profile, retain the existing explicit profile/default credential chain. Stop before execution for explicit profiles differing from configured profiles. Continue account/region confirmation.

Use `awsAccountId` for explicit account ID settings/names during resource creation and target identification. Use `awsExecutionAccountId` as owning/source account for policies authorizing resources created in the same target. `awsExecutionAccountId` is a string of 12 ASCII digits also used to match the authentication account for AWS operations. If omitted, use `awsAccountId`; stop when the caller account differs from configuration. Configuration alone does not switch authentication. In the example above, the selected profile's caller account must be `210987654321`.

For example, in this target's VPC Flow Logs trust policy, `aws:SourceAccount` is `210987654321` and `aws:SourceArn` is `arn:aws:ec2:ap-northeast-1:210987654321:vpc-flow-log/*`. Both conditions match the actual Flow Log owning account ([official AWS Flow Logs trust policy specification](https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs-iam-role.html)). Align permission policy `Resource` ARNs and `Principal` with actual reference-target owning accounts too; retain the specified account for explicit cross-account references.

CFn `AWS::AccountId` is the actual stack creation account ([official AWS pseudo parameter specification](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/pseudo-parameter-reference.html)). If the two IDs differ, implementations including `awsAccountId` in names etc. use a separate explicit parameter. Implicit AWS API owner validation uses the execution account; preserve explicit design account properties and cross-account references.

Do not use aliases when an environment has only one target. For multiple logical destinations, assign human-confirmed aliases to all targets; different aliases may have the same AWS account ID. Aliases must be lower-kebab-case and unique within the same environment; values consisting only of 12 digits are prohibited. The target directory is the alias when present, otherwise `awsAccountId`. Use the same IaC engine also for targets in the same environment/execution account.

## Task transition

For repository changes, register `tasks/<task-name>.md` according to the [task contract](framework/rules/task-contract.md). Read-only investigation/chat-only consultation require no contract. Use the corresponding workflow for each phase's procedures.

Reservations are scoped to the Git worktree, identified by a fingerprint of its worktree-specific Git directory, independently of the branch. Different worktrees can reserve the same repository-relative file. Within one worktree, only overlapping files become Deferred; Active files continue, including when the Deferred output is under `issues/`.

Write workers automatically refresh reservations, finish Active work first, then retry Deferred outputs every 30 seconds for up to 20 attempts under the existing registration lock. Agents run `python framework/scripts/task_contract.py --task-file tasks/<task-name>.md --wait` themselves after Active work, then immediately continue acquired files; humans need not monitor or resume. At exhaustion the execution ends cleanly with unfinished Deferred work retained, neither failed nor completed. Normal reexecution acquires available files automatically. `--resume` remains for real suspended errors. Keep the task `running` while Deferred work remains; after all requested work and the successful final loop, use `--complete`. Foreign tasks cannot be selected or executed in this worktree.

## Task contract and types

Record exactly one of the following in the active prompt's `## Task contract`.

```md
- Task type: `<task-type>`
```

For `infrastructure` tasks, also record exactly one of the following in the same Task contract.

```md
- Infrastructure phase: `<implement-or-deploy-or-update-or-destroy>`
```

Allowed task types:

- `initialization`: Confirm required values with the human and initialize project topology/target paths.
- `design`: Update detailed design and corresponding service models; finish after local validation.
- `infrastructure`: Create/validate IaC in the `implement` phase, deploy/apply existing IaC in the `deploy` phase, or reflect human uncommitted design differences into IaC and deploy/apply in the `update` phase, or explicitly delete designed CloudFormation stacks in the independent `destroy` phase. IaC and desired design remain unchanged during destroy.
- `scenario-test`: Update scenarios, test implementation, execution, and scenario-scoped current results, then finish.
- `governance`: Change repository rules/workflows.
- `catalog-maintenance`: Maintain materials catalogs within explicit scope.
- `migration`: Execute only migration defined by the active prompt.

The human explicitly starts each task independently. Do not automatically create or execute the next task after completion.

Each active task has the following machine-readable completion contract.

```md
## Required changes

- [R1] 実施内容

## Acceptance checks

- [R1] `changed:path/to/file`
- [R1] `check:registered-check-id`
```

Follow [Acceptance contract](framework/rules/task-contract.md#acceptance-contract) for Acceptance check definitions.

## Roles

### Human

- Fill in the system overview as needed
- Answer Ask questions and approve design decisions
- Decide the task type/scope to execute
- Explicitly authorize deploy/apply
- Separately start necessary scenario-test tasks

### Codex

- Execute only within active prompt, task type, and repository rule scope
- Finish design tasks with detailed design/service models. Only if the chatbot specifies existing-resource retrieval, read-only AWS APIs may reflect selected properties and necessary non-ARN current identifiers
- Execute only one of `implement`, `deploy`, `update`, or `destroy` in infrastructure tasks
- Change only scenarios/current results in scenario-test tasks
- Do not automatically proceed to the next phase after task completion

## Initial detailed design

Initial design uses an Ask workflow; implementation occurs in an independent `design` task.

1. Confirm the system overview, existing designs, and related materials.
2. Prioritize undesigned services prerequisite to mandatory services.
3. Ask design decisions in batches of usually 5–8.
4. If the design can be completed only with human-decided values, output completed model properties per file and show Markdown/JSON artifact generation destinations.
5. When using current values of existing AWS resources, the chatbot determines target services/resource types/properties and outputs a self-contained Codex prompt including read-only retrieval instead of completed Markdown.
6. The Codex design task validates target context; after the human selects resource candidates, directly reflect differences for selected properties into `model/**` and generate Markdown/JSON artifacts.

Separate chat completion reports from Markdown to save. Write chat and Markdown descriptions in Japanese; follow `framework/rules/detailed-design.md` for the authoritative format of saved Markdown. For confirmed designs requiring JSON documents such as policies, refer from Markdown to service-owned JSON artifacts under that rule. Update model properties first and generate Markdown/JSON artifacts; design tasks do not change CloudFormation/Terraform, AWS mutation, scenarios, or scenario results. Existing-resource retrieval may reflect only necessary non-ARN current identifiers into observed values.

Per-resource `desired.resource.<nnn>.resourceMode` permits only `CREATE`/`IMPORT`. Unspecified mode is CREATE-compatible. Apply existing naming/mandatory Name tag policies to CREATE and include it in IaC generation. IMPORT retains existing AWS actual/current values in design/models and permits framework naming mismatches and absent Name tags. Do not perform AWS changes, IaC generation, CloudFormation Resource Import, or Terraform import. Separate display labels from AWS properties. See [model contract](framework/rules/model-information.md#resource-management-mode) for details.

## Post-design SDD

For new design, save model properties with the Codex prompt output by `framework/prompts/chatbot/service-design.md` and generate detailed design Markdown, create/validate IaC with `03_implement.md`, and deploy/apply with `04_deploy.md` in a separate task.

When humans directly change existing detailed design and reflect uncommitted differences into IaC through deploy/apply, use only `framework/prompts/codex/05_update.md`. Do not execute `03_implement.md` and `04_deploy.md` individually.

For either workflow, use `framework/prompts/codex/06_scenario-test.md` in a separate task after deployment completion only when application behavior confirmation is necessary. See `framework/prompts/README.md` for detailed usage distinctions.

## Operating model

1. The human decides the type/target scope of an independent task.
2. Codex reads the active prompt, `AGENTS.md`, and related rules; work only within the same task type.
3. `design` tasks update intended design/service models and finish. Include direct reflection of differences from current values through read-only AWS APIs only when existing-resource retrieval is explicit.
4. The `infrastructure` task's `implement` phase finishes with IaC creation/local static validation.
5. A separate `infrastructure` task's `deploy` phase confirms CloudFormation change sets or Terraform plans using existing IaC, deploys/applies, and finishes with post-success observed value updates.
6. The `infrastructure` task's `update` phase performs Markdown generation, IaC reflection, deploy/apply, and observed value updates within one task without changing human uncommitted model properties.
7. Start `scenario-test` tasks separately; update only specified scenario tests/current results.
8. Even if scenario tests fail, do not proceed within the same task to design changes, IaC repair, redeploy, or remediation task creation.

By default, do not save non-scenario task verification output in the repository; record it in Codex completion reports.

## Detailed design for CFn-unsupported resources

Separate targets that may be recorded in detailed design from those creatable with the selected IaC engine. `Macie.ClassificationJob` and `QuickSight.Group` are API-only design targets based on official API specifications. Macie Jobs may appear alongside CFn-supported `Macie.Session` in the same `macie.md`, and QuickSight Groups in `quicksight.md`, in ordinary resource overviews/detail tables.

- API selection lists/fixed schemas: Each resource type in `framework/materials/api/` and its same-named `.json`
- Schemas retain official specification URLs, API versions, source SDK model hashes, confirmation dates, and CFn non-support.
- Use one row per API root property. Retain Macie Job nested settings in JSON; identify QuickSight Groups by `AwsAccountId`, `Namespace`, and `GroupName`.
- For Macie `jobId` and QuickSight Group `PrincipalId` as `IDENTIFIER_OUTPUT`, separate desired logical references from observed current IDs. QuickSight Group `Arn` is also API output, but do not save ARNs. Reference Groups with resource links in DataSource `Permissions[].Principal`.
- Manage QuickSight Groups with `CreateGroup`, `DescribeGroup`, `UpdateGroup`, and `DeleteGroup`; retrieve candidates with `ListGroups`. Only Description can be changed with `UpdateGroup`. Group membership is a separate API resource.
- CFn type resolution: `python framework/scripts/design_catalog.py --cloudformation-type Macie.Session` succeeds; `Macie.ClassificationJob` and `QuickSight.Group` fail as unsupported. Do not treat API-only resources as completed through CFn implementation.
- Checksum confirmation: `python framework/scripts/design_catalog.py`. Maintain API catalogs/schemas in explicitly scoped `governance` tasks; after aligning specifications, selection lists, display definitions, and focused checks, use `python framework/scripts/design_catalog.py --write-lock` to update `framework/materials/api-catalog.sha256`. Do not change them in ordinary tasks or automatically register unknown resources.

This support extends through detailed design, validation, and model generation. Handle API resource creation automation, Custom Resources, switching to Terraform, and consumer synchronization through separate explicit requests.

## Materials catalog

`framework/materials/aws/` is a curated partial catalog created from the AWS CloudFormation Resource Specification, selecting candidate items for detailed design. Do not abolish it or use it to mechanically publish all provider schema items in design documents.

- Provenance and counts: `framework/materials/catalog.properties`
- file integrity: `framework/materials/catalog.sha256`
- check: `python framework/scripts/update-catalog-lock.py`
- Lock update after authorized catalog maintenance: `python framework/scripts/update-catalog-lock.py --write`

Do not change `framework/materials/aws/*.properties` in ordinary project tasks. If resources are missing, update through a dedicated catalog-maintenance task specifying source specification version and target resources.

When adding/removing resources, include and update `framework/rules/resource-layout.json` display policies in the same task's Allowed paths. Explicitly specify independent display or integration into parents for every catalog resource; reject undecided cases in the local loop. Confirm ownership, multiple children, shared/multiple targets, and external references; if conditional integration is needed, first implement its decisions/validation in the framework. Currently, S3 BucketPolicy and KMS Alias integrate into parent detail tables; others retain independent display. Follow `framework/rules/detailed-design.md` and `framework/rules/model-information.md` for KMS Alias identification markers, references, and models.

`framework/materials/cloudformation-schema/ap-northeast-1/` retains full properties/types/constraints of official CloudFormation provider schemas for resource types selected in properties. `framework/materials/cloudformation-schema.properties` is authoritative for target counts. It supplies validation for design values and CloudFormation template property names, `type`, `enum`, `pattern`, length, range, and `required`.

- provenance: `framework/materials/cloudformation-schema.properties`
- file integrity: `framework/materials/cloudformation-schema.sha256`
- offline check: `python framework/scripts/cloudformation_schema.py`
- Explicit refresh from official regional schemas: `python framework/scripts/cloudformation_schema.py --write`

Ordinary local loops validate snapshot/properties correspondence without network connections. Execute refresh only in explicit governance or catalog-maintenance tasks incorporating official schema updates. For CloudFormation templates themselves, perform provider schema validation with target-region `cfn-lint`, then syntax validation with `aws cloudformation validate-template`.

### When waiting stops in VS Code GitHub Copilot Autopilot

1. **Do not add running loops.** Note the log directory at start; check `timing.jsonl` and per-check `.log` for the same execution. Do not conclude Python stopped from tool timeout alone. When checking PIDs, also match commands/start times. Do not edit validation inputs during execution.
2. **Isolate command tracking termination.** VS Code `chat.tools.terminal.enforceTimeoutFromModel` (Experimental) ends command tracking at the agent-specified timeout and returns output collected so far. If the installed version has this setting, compare `false` at workspace scope only when tracking timeout is confirmed as the cause; restore afterward. This setting does not fix session disconnection. [Official settings list](https://code.visualstudio.com/docs/agents/reference/ai-settings#agent-tools)
3. **Run from an ordinary terminal.** For long checks, the human runs the above command in a VS Code ordinary terminal or OS terminal and asks Copilot to check the displayed log path. This reduces dependence on agent tool waiting. Survival of OS sleep or terminal termination requires separate confirmation.
4. **Check evidence of session stops.** Temporarily set GitHub Copilot / GitHub Copilot Chat to Trace with `Developer: Set Log Level`; check errors at the same time through `Output: Show Output Channels`. In versions with Agent Debug Logs, also compare model requests/tool calls and distinguish request limits, communication errors, and extension/terminal anomalies. `chat.agent.maxRequests` limits request count, not execution duration. Review settings only if a request-count limit is actually reported. [Official diagnostics](https://code.visualstudio.com/docs/agents/agent-troubleshooting/troubleshooting), [Request settings](https://code.visualstudio.com/docs/agents/reference/ai-settings#agent-behavior)
5. **Confirm results in the same task.** After disconnection, reread this task's `tasks/<task-name>.md` and saved logs. Confirm `loop_end`, completion of all checks, and unchanged validation inputs before reporting success/failure. If `loop_end` is absent and actual processes have already exited, rerun the full loop. Do not call intermediate logs PASS or proceed to another task.

The local loop validates common checks for task type, infrastructure phase, task scope, project topology, catalog/schema integrity, and IaC engine selection, and design values/service models/observed ARNs within Validation scope. Overall validation also includes repository consistency of IaC contents and scenarios/results; perform actual mandatory IaC/deployment validation separately per phase. System Overview `UNSET` does not cause validation failure. Ordinarily separate IaC creation and deploy/apply into different tasks; only reflection of design manually edited by the human in model properties executes as one task in the dedicated `update` phase.

Design update order is “confirm catalog selection items/naming rules → update model properties → temporarily generate/validate all target Markdown/JSON → save after all succeed.” On generation failure, do not change saved displays; repair properties as authority and rerun. Ordinary sync does not overwrite models from Markdown. Adoption of old formats is limited to `sync-model.py --import-markdown --write` in explicit migration tasks; do not overwrite existing models.

### S3 placement of CloudFormation templates and local artifacts

The controller passes templates directly as before when the submitted template is at most 51,200 bytes; above that through 1 MiB, upload to the specified bucket and create change sets from S3 URLs. Stop above 1 MiB. Small templates require no placement bucket configuration.

Specify destinations in target `cloudformation-stacks.properties` as follows. The following is a format example; confirm bucket names, StackName, and sources in actual design. The S3 model is authoritative for bucket names/settings; retain only references here.

```properties
desired.deployment.templateBucket=[app-dev-assets](s3.md#s3-app-dev-assets)
desired.deployment.templateKeyPrefix=cloudformation/templates/
desired.artifact.001.stack=cfn-stack-app-dev-job
desired.artifact.001.resource=FunctionA
desired.artifact.001.property=Code
desired.artifact.001.source=infra/cloudformation/artifacts/function-a.zip
desired.artifact.001.bucket=[app-dev-assets](s3.md#s3-app-dev-assets)
desired.artifact.001.keyPrefix=lambda/functions/
```

Determine files used by each Lambda from resource/property-to-source mappings. Explicitly state each mapping even when multiple Lambdas use the same ZIP. Specify each entry's bucket when destinations differ. Stop if the original template's S3 bucket/key prefix differ. Retain existing undeclared S3 references.

After uploading local artifacts, generate an execution copy outside the repository replacing only declared S3 keys/versions with content hashes. Lambda ZIP placement and CFn template S3 submission are independent; ZIPs may be uploaded while small templates are submitted directly. Do not automatically build, create buckets, add permissions, or remove past artifacts during deploy. Create initial buckets with small templates; after success, execute consuming stacks.

Validate the whole scope locally; perform upload/checksum confirmation, AWS template validation, and change set creation/execution in each stack's order. Retain the session and adjacent `.files` directory until resuming the same task. Stop resume/execution if input files, execution copies, or uploaded objects change. See [CloudFormation rules](framework/rules/cloudformation.md#s3-deployment-artifacts) for corresponding properties, permissions, and retention policies, and [model rules](framework/rules/model-information.md#cloudformation-s3配置) for the authoritative format.

For CloudFormation deploy failures, follow [Controlled deploy repair](framework/rules/cloudformation.md#controlled-deploy-repair); execute/validate only repairs uniquely determined from authoritative information in the same session and continue remaining stacks. Ask the Human about external information, design decisions, rollback that cannot be safely recovered, and unapproved delete/replacement.
