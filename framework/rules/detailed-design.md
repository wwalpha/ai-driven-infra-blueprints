## Resource management mode

Use `desired.resource.<nnn>.resourceMode=CREATE|IMPORT` in `model-information.md`. Unspecified values retain CREATE compatibility. Retain actual design values for both CREATE/IMPORT in the same detail tables. Retain resourceMode only in framework metadata of authoritative properties. Do not generate resource-mode/resource-entry comments in Markdown; display validation references model categories and numbers by anchor. Do not include them in AWS property tables.

IMPORT retrieves selected AWS actual/current configurations through authorized read-only retrieval and retains them in properties and detailed designs. Save names/values as-is even if they differ from framework naming conventions; do not change AWS resources or include them in IaC generation. This is separate from CloudFormation Resource Import/Terraform import; do not save provenance.

Apply the following mandatory Name policy and naming patterns only to CREATE. If IMPORT has no Name tag, omit rows without making this a blocker or creating tags/provisional values. Display existing names when present; for VPC/Subnet/RouteTable/Flow Log/VPCEndpoint/Instance named by Name tags without names, use human-confirmed display labels or type-name displays for single resources of a type. Do not copy display labels into AWS properties. Retain internal logical IDs, anchors, row order, schema, and reference validation.

## Policy account selection

- Follow [Credentials and account](project-configuration.md#credentials-and-account) for common account selection. The following are policy-specific application examples and validation.
- In VPC Flow Logs trust policies, use the execution account for both `aws:SourceAccount` and account portions of `aws:SourceArn`. For example, if the execution account is `222222222222` and region is `ap-northeast-1`, these are `222222222222` and `arn:aws:ec2:ap-northeast-1:222222222222:vpc-flow-log/*`, respectively. These match Flow Log owning accounts and ARNs ([official AWS specification](https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs-iam-role.html)).
- Match accounts in trust/permissions policy Conditions, `Resource` ARNs, and `Principal` to actual referenced owning/source accounts. Retain accounts of human-explicit cross-account references; do not batch-replace numbers or ARNs in policies. Stop without inferring values if references are unconfirmed.
- In `KeyPolicy` for KMS Keys to CREATE in the same target, use the execution account for both account Principal `arn:aws:iam::<account>:root` enabling IAM permissions and the same target's Macie service-linked role `arn:aws:iam::<account>:role/aws-service-role/macie.amazonaws.com/AWSServiceRoleForAmazonMacie`. If `awsAccountId=111111111111` and `awsExecutionAccountId=222222222222`, account portions of both ARNs are `222222222222`. `Resource: "*"` represents that KMS Key; do not replace it with an account ID ([official KMS specification](https://docs.aws.amazon.com/kms/latest/developerguide/key-policy-default.html), [official Macie specification](https://docs.aws.amazon.com/macie/latest/user/discovery-supported-encryption-types.html)).
- Validate root/Macie role AWS Principals in KMS KeyPolicy Allow Statements from authoritative models before generation and in local loops, whether strings or arrays. If humans explicitly specify Principals differing from execution accounts as cross-account permissions, write connection purposes and `cross-account:<完全なPrincipal ARN>` separated by whitespace in those policy rows' existing `comment`. Exempt only those exact-match Principals; do not interpret explanations containing only account numbers, specifications of other ARNs, or ARN presence itself as cross-account approval. Stop without changing values if unconfirmed. Do not apply this CREATE matching to IMPORT retrieved policies or other Principal types.
- Save policies confirmed in design tasks to authoritative model documents and generate JSON/Markdown. If infrastructure tasks detect mismatches between approved models and execution accounts, report target policies and missing design corrections and stop without implicitly editing models.

## Existing resource configuration

Only when chatbots specify retrieval of current values of existing AWS resources may Codex `design` tasks perform the following.

- Limit retrieval to target AWS services, catalog resource types, and properties confirmed by chatbots. Include detailed-design-only `.Name` properties for `EC2.VPC`, `EC2.Subnet`, `EC2.RouteTable`, and `EC2.FlowLog`, and formal mandatory Name tag `Tags[].Key` and `Tags[].Value` for `EC2.VPCEndpoint`/`EC2.Instance`; do not automatically extend scope to other services, unselected properties of the same resource types, or properties absent from materials.
- Before repository changes, validate `project.json` targets, credential caller accounts, and regions through read-only preflight.
- If target `awsProfile` is configured, use it for preflight and all existing-resource retrieval. Explicitly specify the same `--profile` and target region for AWS CLI, and profile/region for SDKs. Reject explicit profiles differing from configuration; use existing explicit profiles/default credential chains only when unset.
- Prefer AWS Cloud Control API List/Read; use target-service-specific read-only APIs only for unsupported resource types. Stop if AWS-value-to-materials/provider-schema-property mappings are not unique.
- Present resource candidates with only minimal information without secrets, such as primary identifiers; do not confirm retrieval targets until humans select them, even for a single candidate. Primary identifiers that are ARNs may be used temporarily only for resource selection and retrieval.
- After humans select resources, check current values and presence/absence of selected properties and target-resource `Name` tags, then directly apply differences. If Name tags exist, retain them in `.Name` for the preceding 4 types, and in formal `Tags[].Key=Name` and corresponding `Tags[].Value` for `EC2.VPCEndpoint`/`EC2.Instance`. Retain unselected resources/properties in existing files; delete selected optional property rows absent from AWS current values. Stop without inventing values if mandatory `Name` tags are absent for CREATE. For IMPORT, retain absence as-is; use the above display rules if names are absent. If corresponding resource sections do not exist, use `.Name` values as heading identifiers for the above 4 types, retrieved Name tag values for `EC2.VPCEndpoint`/`EC2.Instance`, and confirmed resource names for others. Only if internal logical IDs are unconfirmed, ask humans one question and retain them in hidden metadata. Apply the following type-name display rules to types without resource names; if there is 1 of that type, use the resource type without asking for display names. Confirm with humans only display names needed to distinguish multiple resources, then create service metadata, anchors, headings, and tables. Do not omit internal logical ID confirmation.
- Do not display or save sensitive values such as passwords, secrets, tokens, or credentials. Do not save generated ARNs in detailed designs, JSON artifacts, or models; use them only during processing required for resource selection or API execution.
- Do not save resource provenance such as creator, administrator, or externally created status in detailed designs or models. Detailed designs retain configurations existing in target environments in the same resource table format.
- Do not proceed to AWS mutations, IaC creation/changes, deploy/apply, or scenarios.
- Apply `resource-layout.json` to the above section creation as well; do not create independent headings for grouped children. Verify membership from selected parent-property current values and designed-parent current identifiers, and reflect within parent tables. Stop if membership is unknown or parent designs are absent; do not extend scope to unselected resources/properties.

## AWS resource naming

- Before design starts, execute Naming rule coverage check in `aws-resource-naming.md`. Immediately after confirming target resource types/modes and before design questions or design contract registration, pass `check-design-naming.py` for all targets. Do not condition on name values or model presence; do not start/continue design if rules are unregistered, unreadable, or unexecuted. Recheck on resume, target changes, optional Name tag selection, and before saving; report missing types/properties and stop.
- Require `CodeBuild.Project.Name` in detailed designs regardless of provider schema optional status. Retain exactly 1 confirmed non-empty literal row per resource; reject missing, empty, unconfirmed, or duplicate values. Do not substitute Name tags, internal logical IDs, or display labels; stop without inferring values if unconfirmed. Determine this through common name validation in design validation and model generation.
- Apply `framework/rules/aws-resource-naming.md` when newly determining human-selected AWS resource names, identifiers, or `Name` tags.
- Do not automatically require `Name` tags even if root-level `Tags` or `HostedZoneTags` exist. Mandatory targets are `EC2.VPC`, `EC2.Subnet`, `EC2.RouteTable`, `EC2.FlowLog`, and `EC2.VPCEndpoint`/`EC2.Instance`. Represent the first 4 types with 1 `.Name` row each in detailed designs.
- `.Name` for the above 4 types is a detailed-design-only property, not a provider schema resource property. Convert it to a tag with case-sensitive `Name` key during IaC implementation; do not create 2 `Tags[].Key=Name` and `Tags[].Value` rows in detailed designs.
- Retain mandatory Name tags of `EC2.VPCEndpoint`/`EC2.Instance` in formal `Tags[].Key=Name` and immediately following corresponding `Tags[].Value`. Reject differently cased keys and missing, empty, or unconfirmed Values; do not substitute display labels. Do not create design-only `.Name`; display Value in listings, headings, and ordinary reference links, generating anchors from those display names. Retain internal logical IDs in hidden metadata and existing contracts for identifier-reference desired logical references/observed IDs.
- In generated configuration tables for `EC2.VPCEndpoint`/`EC2.Instance`, combine 2 Name tag rows into 1 `Name | <Tags[].Value>` row. Display Value-side comments; retain Key-side values/comments in hidden `ec2-name-tag` metadata of the same row. This is display abbreviation only; do not add `.Name` to models. Retain original Key/Value rows for other tags.
- Number `EC2.Instance` `BlockDeviceMappings[].<field>` consecutively from `BlockDeviceMappings[1].<field>` in configuration tables. Include `[1]` even for a single element; continue multiple elements with `[2]`, `[3]`, and onward. Each element starts with `DeviceName`; assign the same number to all selected items of the same element, such as Ebs. Retain original element order/values; do not shift numbers based on optional item presence/absence.
- Design `Name` tags for other resources only when humans explicitly specify them. For arrays, write `Name` in `Tags[].Key` or `HostedZoneTags[].Key`, and a non-empty name in the immediately following corresponding `Value` row. For objects, write a JSON object with `Name` key and non-empty value in `Tags`.
- If all naming components are confirmed, derive uniquely from patterns; if any component is unconfirmed, ask humans without inferring values.
- Do not automatically change names retrieved from existing resources or confirmed names in existing detailed designs, even if they differ from conventions.
- If mandatory `Name` tags are absent from existing resources treated as CREATE, stop as a blocker without inventing tag values.
- Verify final names conform to provider schemas and service-specific constraints; do not correct through automatic truncation, hashing, or abbreviation.

## AWS service ownership boundary

The file grouping unit for service resource detailed designs is the AWS service ownership boundary representing responsibilities per human-recognized AWS service, not security boundaries or IAM Permissions Boundaries. One service design file owns only one AWS service. `cloudformation-stacks.md` is exclusively for the above deployment unit.

- Target directories use aliases if configured for targets in `project.json`, otherwise AWS account IDs.
- Place files in `docs/designs/<environment>/<target-directory>/<service-id>.md`.
- Use lower-kebab-case Service IDs matching file stems and corresponding `model/<environment>/<target-directory>/<service-id>.properties`.
- Multiple resource types and instances belonging to the same AWS service may share a file.
- Do not include separate AWS services in the same file merely because they are operationally related. Do not determine grouping solely by CloudFormation resource namespaces.
- Child components may share files with parents only when belonging to the same AWS service. Do not treat resources of other AWS services as child components.
- Place IAM Roles and Policies in IAM service files even when dedicated to consuming services.
- Place CloudWatch Logs resources in CloudWatch Logs service files, rather than source-service files.
- Place VPC Flow Logs in Amazon VPC service files, referencing IAM Roles and Log Groups through cross-file references.
- Separate `EC2.SecurityGroup` and its `EC2.SecurityGroupIngress`/`EC2.SecurityGroupEgress` from `ec2.md`, placing them only in `security-group.md`. Design service ID is `security-group`, corresponding model is `security-group.properties`, and anchors follow common resource display-name rules. Do not mix other resource types into this file; point referencing links to dedicated-file anchors as well.
- Retain inter-service dependencies in authoritative models as relative Markdown links and explicit anchors instead of merging files; generate the same references in Markdown.
- Do not create empty design files for unused services.
- Design file boundaries and CloudFormation stack/template boundaries are separate concepts.

## CloudFormation stack detailed design

Before creating/updating stacks in CloudFormation targets, create `docs/designs/<environment>/<target-directory>/cloudformation-stacks.md` per target. This is a deployment-unit detailed design, not a service resource, and does not represent `AWS::CloudFormation::Stack` (nested stacks). Confirm stack names, template filenames, stack-specific parameter filenames, per-stack-instance `DeployOrder`, and per-target `MaxConcurrentStacks` here. Do not infer order from template filenames. Propose order from Import/Export, resource ownership, and change/rollback units; if unconfirmable, ask humans in design tasks. Reference `project.json` for accounts/regions; do not save deployment status, StackId/ARN, or history.

Hide `MaxConcurrentStacks` (integer 1 or greater) in rendered Markdown; do not output `## Deployment設定` or configuration tables. Retain effective values in HTML comments `<!-- max-concurrent-stacks: N -->` immediately after titles; validate model equality and integer constraints. Use 6 columns `No. | Deploy<br>Order | StackName | Template | Parameters | Comment` for `## Stack一覧`, displaying DeployOrder headings on 2 lines. `DeployOrder` is a positive integer with unrestricted intervals; equal values mean the same group eligible for parallel execution. Proceed to the next group only after every stack in the smaller group reaches terminal success. Display in ascending numeric DeployOrder, then ascending string StackName. Display 1 stack instance per row; `No.` is sequential from 1, and `Comment` briefly describes stack purposes/roles in Japanese. Generate `Comment` from model `display.stack.*.comment`; do not treat it as an AWS stack property.

## Markdown structure

Saved Markdown consists, in principle, only of H1 titles, service metadata, `## リソース一覧`, `## リソース詳細`, explicit anchors per resource, resource headings, and resource-detail tables. Security Groups use the attribute-aggregating listings and horizontal rules tables with Direction described below. Resources with policy JSON also have Statement tables or configuration tables generated from JSON as described below. Only when tables cannot represent the content may minimal necessary implementation notes be added.

- Descriptive text, including titles, headings, implementation notes, and `Source / Comment`, must be written in Japanese. Values whose meanings change if translated, such as formal AWS service/resource/property names, logical IDs, code, and JSON keys, may remain in the original language.
- Place exactly 1 `## リソース詳細` after listings and before the first resource anchor. Place all resource details in this section; separate listings and details at the same H2 level.
- Independently displayed catalog-backed resource headings under the detail section use `### <catalog-resource-type>: <resource-name>`. Only when applying the following type-name displays, use `### <catalog-resource-type>` without `: <resource-name>`. Policy-table headings are H4 under resources; do not use headings at or above resource levels for implementation notes either. Resources merged into parents follow common display contracts described below.
- Only `S3.Bucket` uses `### S3.Bucket: <BucketName>`; heading identifiers must exactly match `S3.Bucket.BucketName` values in the same table.
- For all services, heading `<resource-name>` uses confirmed name properties (`Name`, `BucketName`, `RoleName`, `Scheduler.Schedule.Name`, etc.) or selected `Name` tag values from the same detail table. Do not display internal logical IDs in headings, listing ResourceNames, or reference-link display text. For types without catalog name properties, if neither selected Name tags nor existing confirmed display names exist and exactly 1 independent resource of that type exists in the same service file, use resource types as display names in headings, listings, and ordinary reference links. Do not ask for additional display names; generate anchors from resource types as well. Multiple resources of the same type require human-confirmed distinguishable display names; stop if missing. Retain existing confirmed display names/logical IDs. Do not apply this rule to omitted CREATE name properties or missing mandatory Name tags. IMPORT absence of Name tags follows the above exceptions. Do not substitute generated IDs or `PENDING_DEPLOY` for resource names.
- If `KMS.Key` has owning Aliases, use names removing only the leading `alias/` from `KMS.Alias.AliasName` for ResourceNames, detail headings, and ordinary Key reference links, and generate Key anchors from those names. For example, display `alias/venus-dev-log-cde` as `venus-dev-log-cde`. With multiple aliases, use human-confirmed `display.resource.*.label` matching one of their names; if missing/mismatched, stop without selecting the first alias. Apply existing display rules to Keys without designed Aliases. Do not change formal AliasName values, Alias own anchors/reference displays, KeyId, or internal logical IDs through this display conversion.
- Retain internal logical IDs in standalone `<!-- resource-logical-id: <logical-id> -->` lines immediately before explicit anchors. Markers may be omitted if headings and IDs are the same confirmed resource name. Type-name displays require markers; do not infer logical IDs from resource types. Do not display markers on-screen; use them only for model logicalId and IaC identification.
- For types without name properties, permit human-confirmed `display.resource.<番号>.label` as display names even if identical to internal logical IDs. Match corresponding authoritative model `desired.resource.<番号>.resourceType`, `logicalId`, and explicit labels against detail headings, applying only to matching resources. Reject reuse of internal IDs due to missing labels. Hidden logical ID markers remain mandatory in this case; anchors derive from display labels, retaining desired logical reference/observed current identifier separation. Do not use this to substitute CREATE name properties/mandatory Name tags or add catalog properties/Name tags. For IMPORT absence of Name tags, display labels alone may be used.
- If `.Name` exists for `EC2.VPC`, `EC2.Subnet`, `EC2.RouteTable`, or `EC2.FlowLog`, resource names must exactly match `.Name` values in the same table. For IMPORT absence, use the above display rules.
- Do not specify `Environment`, `AWS account ID`, `AWS region`, `Purpose`, or `Deployment state` as file metadata. Reference relevant authoritative sources in `project.json`, `docs/system-overview.md`, active tasks, and `model/**`. Only S3 Bucket placement regions display per-bucket confirmed values in the design-only `S3.Bucket.Region` rows described below.
- Do not create `Design decisions`, `Out of scope`, `Generated values`, or synonymous Japanese sections.
- Write confirmed design values in corresponding resource/component tables.
- Write out-of-scope matters only in active tasks or chat completion reports.

## Resource overview

Each detailed design file places exactly 1 `## リソース一覧` immediately after service metadata. The listing extends until immediately before the next `## リソース詳細`, excluding resource anchors, detail tables, and policy tables.

- Within listings, place one `### <catalog-resource-type>` and table per catalog resource type with detail blocks. Do not create independent listings for grouped child resource types.
- Use 3-column `No. | ResourceName | Comment` tables, displaying 1 resource per row. `No.` is sequential from 1 within each resource-type table. Display corresponding detail-heading identifiers in `ResourceName` as same-file links; briefly describe resource functions, purposes, and roles in Japanese in `Comment`. If multiple resources of a type exist, distinguish each row's purpose. Do not use sentences merely repeating resource types or ResourceNames as Comments, such as `セキュリティグループ（VULNERABILITYSCANCDESECURITYGROUP01）の設定`. Verify Security Group purposes from detailed GroupDescription, communication rules, and consumers; do not infer if unknown. List all detail blocks without duplicates.
- Do not display configuration values, generated IDs, or policy links in listings; retain them in corresponding resource detail blocks. Listings are human-readable guides: generate ResourceName from model name rows, confirmed display labels, or the above type-name display rules, and Comment from `display.resource.*.comment`. Do not duplicate generated tables themselves in models.

- S3 BucketPolicy remains in Bucket configuration tables; derived policy tables also belong to Buckets. KMS Aliases retain existing grouping in the same configuration tables as Keys. Do not arbitrarily merge independent policies targeting multiple resources, such as SQS/SNS, into one target.
- For non-IAM-Roles, display names are JSON link display text, and anchors are `<resource-anchor>-policy-<artifact-id>`. Artifact IDs use existing lower-kebab-case filename stems. Use distinct artifacts for multiple policies within the same resource; stop on anchor collisions. Also make policies configured per array target identifiable from each JSON link.
- Headings are `#### ポリシー：<表示名>` or `#### ポリシー設定：<表示名>`; for all services, do not redisplay formal `Property` or original `JSON` links from configuration rows in derived displays. Derived displays consist of anchors, headings, and Statement or configuration tables. IAM trust policies also include Version tables below. Do not add display names as fictitious resource properties.
- Generate policy tables within owning-resource detail blocks; do not add policy columns to listings.
- Statement table numbering, columns, Principal expansion, Conditions, escaping, omission prohibition, and unknown-element rejection use the same method as IAM below. Omit standalone `Version：` and `Id：` metadata rows across all services including IAM, retaining JSON-body Version/Id. Do not infer non-permissions-policy JSON as Statement format.
- Configuration tables use `Property | Type | Value`, with JSON Pointer for Property and `object`/`array`/`string`/`number`/`boolean`/`null` for Type. Root pointers are empty strings; object keys are in string order, arrays retain 0-based indexes and original order. Escape `~` and `/` as `~0` and `~1` within pointers. Containers with children have display-only `—` Values; empty objects/arrays use `{}`/`[]`. Display all elements without converting structures or types. Configuration-table Property columns and JSON Version/Id keys are not standalone metadata rows, so do not omit them.
- `ECR.Repository.LifecyclePolicy` displays all wrapper settings; if `LifecyclePolicyText` exists, also display parsed JSON string contents in configuration tables. Stop for non-JSON strings or invalid JSON. Do not write displays back into JSON bodies.
- Reject duplicate JSON keys, invalid JSON constants, non-JSON-object artifacts, and other-service-owned artifact references in all formats. FAIL local loops for missing/duplicate/misowned markers or mismatches between tables/listing links and authoritative sources.
- Generation updates only derived policy tables of one specified Markdown. Do not duplicate derived displays in models; retain existing JSON links and canonical hashes.

Display multiple condition values as JSON arrays; do not change condition operators or array structures. Do not split/merge Statements because of Conditions.

## Links and anchors

- Represent related resources with Markdown links in `Value` columns.
- Use relative paths for links.
- Place explicit HTML anchors immediately before resource headings; do not rely solely on renderer autogeneration.
- Anchors join Service IDs and lowercase resource display names with `-`. Replace runs of characters outside `[a-z0-9_.-]` in display names with `-`, removing leading/trailing `-` from display-name portions. Stop on normalized anchor collisions; do not correct using internal IDs. Do not generate display-link anchors from internal logical IDs.
- Because same-name `Config.ConfigurationRecorder` and `Config.DeliveryChannel` are valid within the same service, insert `configuration-recorder` and `delivery-channel`, respectively, between Service IDs and normalized display names regardless of names. If both Names are `default`, use `config-configuration-recorder-default` and `config-delivery-channel-default`. Retain `default` for Name values, listing ResourceNames, detail headings, and link display text; determine types from catalog resource types. Retain hidden logical IDs and desired/observed separation; reject old `config-default` or wrong-type anchors. Continue stopping on same-type normalization collisions.
- For CREATE `EC2.VPC`, `EC2.Subnet`, `EC2.RouteTable`, and `EC2.FlowLog`, `.Name` values are logical IDs; anchors also use the same values lowercased.

- Same-file example: `[flow-log-app-dev-vpc](#vpc-flow-log-app-dev-vpc)`.

Resources omitting markers use confirmed heading resource names as internal identity.
