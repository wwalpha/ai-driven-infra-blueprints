# CloudFormation Rules

- Follow [Credentials and account](project-configuration.md#credentials-and-account) for account/profile/target selection.

Follow [issue-gate](issue-gate.md) for target service stops and exceptions.

- Create, change, and execute CloudFormation only in `infrastructure` tasks.
- Infrastructure task design inputs are approved authoritative model properties entries and required parts/referenced models. Obtain design values from `desired.row.*`, JSON bodies from `desired.row.*.document`, identity/references from metadata such as `desired.resource.*`, and current non-ARN identifiers from `observed.*`. In ordinary deploy, do not additionally read generated service Markdown/service-owned JSON bodies. Map `.md#anchor` using existing model readers and metadata; stop for unknown, unmatched, or ambiguous mappings, without generated Markdown body fallback.
- Retain generated artifact existence verification, existing hash monitoring/reservations, generated artifact validation by sync-model/local loop, and stop conditions. For explicit display defect/mismatch investigation, only necessary corresponding portions may be read. Classify mismatches under Controlled deploy repair below. Do not change intended design.
- If intended design changes are needed, stop without filling values and report that a separate `design` task is required.
- Use only when the active project and target environment/target directory select CloudFormation.
- Preflight and controllers automatically use target `awsProfile` if present. Pass the same `--profile` and target region to direct AWS CLI too (including validate-template, list/get/describe, and observed value retrieval). Reject explicit profiles differing from settings before execution; do not fall back to another profile after authentication failure.
- In YAML CloudFormation templates, use `!` form for every intrinsic function with AWS shorthand; corresponding long-form `Ref:` and `Fn::...:` are prohibited. The sole exception is `!ImportValue {Fn::Join: ['', ['ExportBase', !Ref Suffix]]}` referencing suffixed Exports. YAML cannot directly nest shorthand tags, so only this expression's `Fn::Join` may use long form. Do not use `!Sub` in `ImportValue` values. Array arguments also use shorthand flow form such as `JobId: !Select [0, !Split ['|', !Ref GlueJobDefinition075]]`.
- For `!If` array arguments, place true and false values after the condition name on separate lines at the same indentation for comparison. Retain flow form; for example:

  ```yaml
  Value: !If [ConditionName,
    TrueValue,
    FalseValue]
  ```

- Do not use YAML anchors/aliases or hash merge (`<<:`) in CloudFormation YAML. Explicitly state original values for identical trust policies, IAM/KMS permission Policies, and other setting blocks in each resource. Do not require sharing merely because content is identical; retain per-Role design JSON artifacts and references.
- Under `Resources` in CloudFormation YAML, insert at least 1 blank line between consecutive resources.
- Do not use nested stacks.
- Determine stack/template boundaries by change units, rollback units, dependency direction, and deploy responsibility, not AWS services.
- Default to `1 template = 1 deploy responsibility`, but the same template may serve multiple stack instances. Deploy/update execution units are StackNames in authoritative `cloudformation-stacks.properties`, not template paths.
- CloudFormation target stack creation/update requires stack detailed design from `framework/rules/detailed-design.md`. Resolve each stack instance's StackName, template filename, individual parameter filename, DeployOrder, and target MaxConcurrentStacks from authoritative `cloudformation-stacks.properties`. During deploy, existing `load_units()` confirms equality with generated stack Markdown; AI manual duplicate comparison of the same values is not required. Retain existing sync-model/local loop timing for ordinary service generated artifact validation. Template/parameter locations follow this rule's path conventions. Do not infer StackNames from template/parameter filenames alone.
- Before deploy, match target account/region stacks read-only and confirm designed stack existence, states, parameters, and resource ownership. Distinguish undesigned stacks, same-named stacks differing from design, and designed stacks absent from AWS; do not automatically adopt/change/delete undesigned stacks. Retrieve current stack status from AWS each time; do not save status snapshots in Git.
- Do not interpret disappeared/renamed StackNames in design as existing stack deletion/rename. Decide ending management/deletion under a separate authorized scope with explicit targets/impacts; do not implicitly include it in current deploy/update.
- Do not create standalone templates/stacks owning only CloudWatch Logs resources (`AWS::Logs::*`) and Security Groups (`AWS::EC2::SecurityGroup*`); include them in templates of using resources. Include IAM Roles in templates of directly using resources in the same target when present. For Roles without directly using resources (such as cross-account switch roles), confirm no same-target design resource directly references the Role and confirm its trust policy Principal; record purpose and AssumeRole sources in design before placing only the Role and associated IAM Policy/ManagedPolicy in a dedicated template/stack. Declare `RolePlacement: standalone` directly under `Metadata` in this template. This declaration expresses design decisions, not proof of nonuse in AWS. A template with InstanceProfile added is not Role-only.
- Cross-stack references expose only stable values needed downstream, avoiding unnecessary coupling.
- When using resources outside templates through `!Ref`, `!GetAtt`, `!Sub`, policy/setting strings, etc., identify actual resources and owning stacks. String equality alone does not establish resource references. If another CloudFormation stack in the same AWS account/region owns them, match producer template Outputs against deployed stack exports and confirm necessary values are exported. Stop without guessing unless owning stacks, referenced values, and export names are uniquely confirmed.
- If necessary exports are absent and producers are managed CREATE targets in this framework, add Output/Export for only necessary values to producer templates and deploy producer stacks first in authorized infrastructure tasks. Do not change/deploy consumer templates until terminal success and actual export names/values are confirmed read-only. Do not change export names/values used by existing imports merely for naming format. If producer/consumer cannot be handled in the same task, execute in order within task boundaries.
- After producer export confirmation, consumer templates reference that export name with `!ImportValue`. For references used within strings, pass `!ImportValue` into `!Sub` variable maps or `!Join`; do not leave physical IDs/generated ARNs as literals. Import destinations must be the same AWS account/region; create consumer change sets after producer success. Even when cross-stack ARN exports are needed, do not save generated ARNs as observed values.
- Template `Resources` keys (resource logical IDs) and final `Outputs.*.Export.Name` values must be PascalCase. Start with ASCII uppercase and use only ASCII alphanumeric characters afterward; no hyphens, underscores, or spaces. This rule does not apply to non-exported Output keys or AWS-generated physical IDs.
- For detailed design identifier references to CREATE, resolve logical IDs from Markdown link anchors and generate `!Ref`. Do not hardcode link display text `PENDING_DEPLOY` or physical IDs into templates.
- Uniquely map models to stack resources with resource `cfn-logicalId=<StackName>-<Resources key>`; use only the trailing CFn resource ID in template `!Ref`, `!GetAtt`, and Outputs. Do not use composite IDs as template keys. Do not change anchors, confirmed resource names, or existing CFn IDs. Stop without guessing for invalid/duplicate mappings or unconfirmed final Export Name values including target-specific parameters. Existing stack logical ID/Export Name changes may delete/recreate resources or disconnect cross-stack references; do not automatically change them merely for naming format.
- Even when detailed design tables are integrated, implement CREATE KMS Keys and Aliases as their respective formal CloudFormation resources. Do not generate IMPORT. Retain grouped Alias logical IDs/anchors and set `!Ref` of the Key indicated by `parentReference` in model `parentProperty`. References from S3 to Aliases use the corresponding Alias `!Ref`, not Key references. Do not change existing IaC logical IDs solely because display changes.
- Expose CREATE catalog `IDENTIFIER_OUTPUT` needed by subsequent resources or other stacks in CloudFormation `Outputs` through logical resource references. Generated ARNs are excluded from output collection and observed value persistence.
- Place common templates without aliases in `infra/cloudformation/templates/` and alias-specific templates in `infra/cloudformation/templates/<alias>/`. Share templates for the same alias across environments; do not share across different aliases.
- Place target-specific parameters in `infra/cloudformation/parameters/<environment>/<target-directory>/`. The target directory is the alias if present, otherwise AWS account ID.
- If formal resource name properties or `Name` tags include Environment ID, declare independent `Environment` in template `Parameters` and set `Environment` to the target Environment ID from `project.json` in target-specific parameter files. Compose names in resource properties/tag values using `!Sub`, `!Join`, `!Ref`, etc., treating it like independent components such as AWS account IDs. Do not change confirmed complete names in detailed designs.
- Do not include target Environment ID as a name component in parameter values other than `Environment` (resource names, prefixes, suffixes, etc.) in target-specific parameter files. For example, compose `app-dev-role` inside templates from `Environment=dev` and `NamePrefix=app`. `NamePrefix=app-dev` is a violation regardless of `Environment` parameter presence. Do not hardcode complete names in templates or embed Environment in other parameters to append it twice.
- Manage 1 environment/AWS account with only 1 IaC engine, consistent across aliases sharing an AWS account ID. Also keep engines consistent across targets sharing environment/execution account.
- `AWS::AccountId` used to evaluate local/deploy Conditions, ImportValue, artifact references, and Outputs uses the execution account. Use independent explicit parameters when passing `awsAccountId` into resource names, etc.; do not substitute native pseudo parameters. Actual stack/resource owning accounts are determined by AWS execution destinations.
- Perform authorized operations with AWS CLI.

## Design coverage and CloudFormation support

- Detailed designs/models also contain CFn-unsupported resources. Resolve formal CFn types for every implementation target resource type with `python framework/scripts/design_catalog.py --cloudformation-type <catalog-resource-type>`. Unknown types or `cloudFormationType: null` are failures; do not invent `AWS::` types merely by resource type string replacement.
- `Macie.Session` uses existing CFn schemas. Treat `Macie.ClassificationJob` as CFn-unsupported; do not include Jobs in CFn templates, Outputs, or `!Ref`.
- If the active task specifies only CFn-supported scope, implement that scope and finish. If Jobs are requested for implementation, explicitly state them as unimplemented; do not silently narrow scope or call the request complete. Do not automatically add Custom Resources or other engines for Jobs.
- Even if CFn resources need API resource identifiers, do not generate fictitious `!Ref`. Without approved external input handoff design, report missing dependencies and stop. Do not infer implementation methods from link display current IDs.

## Resource mode boundary

- Only authoritative model resourceMode=CREATE (including unspecified mode) is generated for CloudFormation. Retain IMPORT in detailed designs/properties, outside IaC generation, without AWS resource changes. Do not generate IMPORT in `Resources`. Do not create/execute CloudFormation Resource Import or Import change sets, or migrate existing resources to Stack management.
- IMPORT is a framework design management classification, not CloudFormation import functionality. Do not correct values to framework naming or add/change Name tags.
- Resource implementation, logical ID mappings, identifier references, and Outputs/output generation in this rule apply only to CREATE. Grouped children with independent identities are classified by their own resourceMode. Inline settings follow the containing resource's classification.
- For CREATE references to IMPORT, do not generate fictitious resource references. Without an existing approved handoff design, report what is missing and stop; do not design new external input mechanisms. Do not change external stacks/states owning IMPORT.
- Do not interpret switching already IaC-managed resources to IMPORT as authorization to automatically delete them from templates/configurations or release management. Report impacts and stop when detected.

## Validation and execution

`implement` phase:

1. Before implementing existing templates and before finishing generated templates, perform local read-only mapping validation with `cloudformation_observed.py --environment <environment> --target-directory <target-directory> --stack <StackName>` (repeat `--stack` for each stack). Deploy uses the same `mappings`. Directly match StackNames/template resource IDs with each resource's `cfn-logicalId`; do not use separate mapping tables. Models with legacy logicalId only are limited to unique legacy matching. Evaluate Conditions with stack-specific parameters/defaults and account/region/StackName; validate CREATE, formal types, unique mappings, identifier rows, necessary GetAtt Outputs, and duplicate ownership only for active resources. Stop on unresolved, cyclic, or non-boolean Conditions; do not include inactive resources in identifier validation/ownership decisions. Do not automatically add identifier rows; aggregate deficiencies per stack. Absent new templates are not pre-implementation deficiencies; confirm model/placement inputs and always run this common validation after generation.
2. Run static checks of properties, types, and constraints based on CloudFormation provider schemas with target-region `cfn-lint`.
3. Do not execute AWS APIs, `aws cloudformation validate-template`, change sets, or deploy/update.

`deploy` phase:

1. Read target templates and rerun target-region `cfn-lint`.
2. Validate template syntax with `aws cloudformation validate-template`. This command alone does not replace property validation.
3. Create change sets and confirm scope, delete, and replacement.
4. Do not introduce human review uniformly stopping all change sets. Wait for human confirmation with an explanation according to `framework/prompts/codex/04_deploy.md` only for unapproved delete/replacement.
5. Proceed to execution only if the active prompt authorizes deploy/update, change scope matches it, and delete/replacement is preapproved or approved by the human after change set creation.
6. Classify failures under Controlled deploy repair; minimally repair/validate/retry only AUTO_REPAIRABLE in the same session.

`framework/scripts/cloudformation-deploy.py` enforces multi-stack queues, order, parallel limits, and failure stops. Process only Deployment scope StackNames in numeric DeployOrder ascending order and StackName order within groups. Only stacks in the same DeployOrder group may run concurrently; RUNNING count must be at most MaxConcurrentStacks. Reuse free slots for the same group's queue, not fixed batches. Proceed to the next group only after terminal success and observed value reflection of the entire group. Values need not be consecutive. Do not convert DeployOrder to CloudFormation resource `DependsOn` or add dependency fields to stack models.

Immediately before consumer change set creation, interpret `!ImportValue` with the existing cfn-lint decoder, resolve referenced Export names using stack-specific parameters/defaults and account/region, and confirm existence with target `list-exports`. Evaluate Conditions; scan only selected `!If` branches and active resources/Outputs. Stop for unresolved, cyclic, or non-boolean conditions; do not require ImportValue in unused branches. Unresolved expressions, absent Exports, and unsuccessful in-scope producers are BLOCKED. Explain incorrect DeployOrder and Import/Export contradictions; do not add out-of-scope producers, change order, or automatically repair IaC/intended design. Consumer-only deploy is permitted if out-of-scope producer Exports already exist. Stop for Transform-dynamically-generated imports that cannot be resolved in advance.

On failure/rollback, blockers, or unapproved delete/replacement, do not start new units; confirm only running stacks through terminal states. Distinguish SUCCESS, FAILED, BLOCKED, and NOT_STARTED per StackName. Status API errors are not terminal failures: stop queues and retry only running stack retrieval. Do not automatically rollback, delete, or redeploy successful stacks. Rollback/delete is permitted only under the provenance-backed failed CREATE cleanup exception below.

`update` phase:

1. Generate Markdown without changing model properties manually edited by the human before task start.
2. Create/change target templates using the same `cfn-lint` as implement phase.
3. Continue with the same preflight, `aws cloudformation validate-template`, change set checks, execution, and completion confirmation as deploy phase.
4. Permit only target template uncommitted diffs generated in this phase for deploy.

## Controlled deploy repair

Do not stop for Human input merely upon failure detection. Stop existing queues, drain RUNNING peers to terminal states, and synchronize successful peer observed values before controller diagnosis/classification. Retain events matching execution tokens in the session; do not retrieve the same diagnostics twice.

- `AUTO_REPAIRABLE`: For in-task-scope CREATE-managed resources, repair values/mappings are unique from authoritative model typed properties/documents, resource-owned cfn-logicalId, project metadata, and confirmed Exports/owners, allowing minimal repair of only reserved IaC without intended design/scope changes. Reuse existing `issues_iac.Comparison` and catalog row projection. Use error text to select failed resources/properties, not as value evidence. Replace CatalogId with `AWS::AccountId` only when the model's confirmed value equals the deployment account itself.
- `HUMAN_REQUIRED`: Missing external/IMPORT handoffs, unconfirmed/multiple solutions, unknown account/region/ownership/cross-account intent, architecture/design changes, external-owner IAM/KMS changes, scope expansion, impacts on other stacks through shared templates, or inability to prove safe rollback recovery. Do not invent values, exports, resources, or parameters.

Require contract `Controlled repair: allowed`, external `Deploy repair session`, and exact target file Modified files/Allowed paths reservations. Do not grant writes to all infra. Do not change general implement/update responsibilities or Terraform failure handling. New design values, artifact builds, and resource placement decisions are not deploy repair.

Save failure classes, target paths, old/new file digests, old/new unit digests, exact external repair candidates, repair intents, validation, old change sets, and retry stages in sessions. After interruption, only recorded old/new bytes are recovery candidates; rerun affected validation. Continue stopping on nonrepair IaC changes, intended model changes, or task scope changes. Validators permit only exact IaC changes matching repair history/current bytes in the same session. Classify structured static lint diagnostics by the same criteria; pre-AWS-execution repairs perform no cleanup. For stale values of explicit parameters consumed by only one unique property, repair only parameter files while retaining template Ref. Discard old change sets/delivery/client tokens; rerun lint only for affected stacks, existing validator affected-service schema/naming/policy/model-generated equality, common task checks, and resource mapping/ownership checks. Then generate validate-template and new change sets and reapply existing delete/replacement approval. Do not add all framework regression to deploy runtime.

`ROLLBACK_COMPLETE` may be a cleanup candidate only if this session confirmed absence and created a CREATE change set, and returned StackId matches execution token StackId. Do not automatically delete if DeletionPolicy/UpdateReplacePolicy Retain/Snapshot, custom/nested resources, DELETE_SKIPPED, existing resources, or termination protection exist. Match exact StackId current/resource terminal states; delete only failed CREATE shells and rerun CREATE after DELETE_COMPLETE confirmation. Do not infer provenance from same names. Diagnose `ROLLBACK_FAILED` and `UPDATE_ROLLBACK_FAILED` and hand off to Human because template repair alone cannot prove safe normal rollback continuation. Existing stack deletion and automatic `ResourcesToSkip` use are prohibited.

At most 3 repair iterations for the same logical failure class (logical ID + property). Stop for Human input if the same repair candidate recurs, or the same failure persists after repair with no model diff and no provable material progress. Do not redeploy successful units; after repair success, continue remaining units in the same controller under original DeployOrder, parallel limits, and dependency barriers.

## Delete and replacement confirmation

- `Remove`, `Replacement: True`, and `Replacement: Conditional` require confirmation regardless of resource type. If `Action` or `Replacement` values cannot be determined, stop without treating changes as approvable.
- Do not treat unapproved delete/replacement as deployment failure/task completion; wait for human confirmation without executing created change sets.
- After human approval, retrieve the same change set ID again in the same task; execute it only if status is `CREATE_COMPLETE`, execution status is `AVAILABLE`, and approved logical IDs, actions, replacements, and `PolicyAction` match.
- If change sets expired, were recreated, or changed, do not use previous approval; explain new contents and reconfirm.
- Do not execute change sets with approval for only a subset of changes. If template repair, resource retention, or removal from CloudFormation management is needed, stop without IaC changes in the current deploy/update phase.

Stop in the following cases.

- Validation failures without unique repair evidence
- required input missing
- AWS account or region mismatch
- Delete/replacement actions cannot be determined
- Intended design is deficient or needs changes

When the active prompt limits targets, implement phase may process only some templates and deploy phase only some stacks/resources, then finish. Do not automatically proceed to remaining resources, other stacks, or scenario tests.

Follow [observed-values](observed-values.md) for identifier collection/synchronization after success, and [task-contract](task-contract.md) and [loop-engineering](loop-engineering.md) for task finish.

## S3 deployment artifacts

- Target `cloudformation-stacks.properties` is authoritative for placement/local file mappings. `desired.deployment.templateBucket` is a BucketName display link to the same target's S3 design; `templateKeyPrefix` is a confirmed prefix. Specify both or omit both. Do not duplicate bucket names between project settings/models.
- `desired.artifact.<id>` explicitly states every `stack`, `resource`, `property`, `source`, `bucket`, and `keyPrefix`. Stack is a designed StackName, resource a template logical ID, and bucket a link to the same target's S3 design. Sources are only repository-relative files under `infra/cloudformation/artifacts/**`; reject directories, external paths, or symlinks escaping outside. Do not infer resources from filenames. Multiple Lambdas may explicitly use the same source.
- Lambda Function `Code` / LayerVersion `Content` handle built ZIPs, Glue Job `Command.ScriptLocation` scripts, and StepFunctions StateMachine `DefinitionS3Location` / ApiGateway RestApi `BodyS3Location` definition files. Do not infer support for container images, nested stacks, Transform, or unknown properties. Retain S3 references without declared artifacts as references to already placed files.
- Original templates declare formal S3 bucket/key (or S3 URI); match resource types/properties, resolved bucket names, and keyPrefix to mapping tables. Stop for values not determinable by parameters/defaults, Ref, Sub, Join, or confirmed ImportValue. Execution copies may change only declared property S3 keys/versions or S3 URIs, not bucket expressions, other settings, or original IaC/parameters/models. Original keys are designed values under specified prefixes; mapping tables are design inputs authorizing replacement with content-hashed keys.
- Confirm whole-scope cfn-lint/files/input hashes first. AWS validate-template runs when each stack's turn arrives. Enable placement buckets in groups after producer success/observed reflection; do not proceed to consumers before bucket creation.
- S3 placement uses the same target account, region, and profile. Confirm with GetBucketLocation and expected-bucket-owner; do not automatically create specified buckets or fall back to others. Initial bucket creation stacks send templates at most 51,200 bytes directly; run using stacks after success. Do not automatically run out-of-scope bootstrap.
- Place at `<keyPrefix><内容SHA256><file拡張子>` using CLI `put-object --if-none-match '*'` and SHA256 checksums. Reuse files with identical checksum/size at the same bucket/key; stop without overwrite on mismatch or missing permissions. Share when multiple resources use the same source/prefix. Fix object versions too for Lambda/Layer/definition properties and template URLs when versioned objects are used.
- Controllers save execution template copies in `.files` directories beside external sessions and rerun cfn-lint. If actual sent UTF-8 bytes are at most 51,200 bytes, use template-body; above 51,200 bytes through 1 MiB, place in specified buckets and use template-url; above 1 MiB, stop. Small templates require neither TemplateBucket configuration nor S3 operations. Pass the same input to validate-template and create-change-set.
- Create change sets only after placement success and checksum/size confirmation. Sessions retain input hashes including sources, execution template hashes, bucket/key/version/checksum, and the same change set ID; recheck on resume and before execution. Do not execute changed ZIPs or placed objects with previous approval. After interrupted upload, objects with identical hashes may be reused. Confirm RUNNING stacks through terminal states under existing drain rules.
- Permit executors GetBucketLocation, ListBucket, GetObject (GetObjectVersion when using versions), and PutObject on placement buckets for necessary prefixes. Also design permissions for CloudFormation/related services to retrieve artifacts. Encryption follows designed bucket settings; for SSE-KMS, confirm necessary KMS permissions for upload, checksum confirmation, and service retrieval. Do not automatically add permissions or make public.
- Do not automatically delete past artifacts during deploy because rollback needs them. Determine retention/lifecycle through explicit S3 design. Do not persist execution snapshots such as status, URLs, object versions, or checksums in models/Git.

## Controller sessions and execution timing

Ordinary deploy completes all DeployOrders in one controller launch. For sequential execution, pass all Deployment scope in the same launch and use `--sequential` to limit concurrency to 1. Do not change designed MaxConcurrentStacks; include execution limits in session immutable inputs. Do not bypass stop conditions by splitting scope/sessions per stack. After failure/blockers, do not start remaining stacks in outer loops; report unstarted stacks including dependent consumers as NOT_STARTED. Perform group-boundary observed updates/service generation inside controllers; save only successful barriers in sessions. `--pause-after-group` may be used only for explicit update producer/consumer IaC changes. Resume the same session for approval, failure, or interruption without rerunning successful stacks.

After reading all scoped templates/parameters, confirm all unique per-resource cfn-logicalId, Condition, resource type, identifier row, necessary Outputs, and owning stack mappings using the same local read-only validation as implement. Build StackName + template resource ID indexes once; aggregate diagnostics per stack without stopping at the first mismatch. If any mismatch exists, set STOPPED without cfn-lint or change set creation. Save diagnostics in session validationErrors and each stack's preflightErrors; retain NOT_STARTED for unstarted stacks. These are preexecution diagnostics, distinct from AWS creation failure. Reconfirm mappings on resume too; reuse lint results for the same validationDigest only on success.

Session v2 validationDigest includes IaC, parameters, artifacts, framework, project, and Python. Reuse only PASS with identical digests; revalidate or reject changed inputs under immutable guards. Revalidate and migrate v1. Caches do not replace actual AWS context, issues, Exports, change sets, or object checksum/version matching immediately before execute.

Prepare same-group change sets within MaxConcurrentStacks in advance, parallelizing completion waiting and read-only polls of running stacks. Only the controller main thread performs state updates, approval decisions, execution, next-group decisions, and session saving. Retain event client token/stack status matching.

Session metrics retain controllerInvocationCount, validationCount, validatedInputDigest, deployOrderCount, awsPollCount, observedSyncSeconds, inputLoadSeconds, mappingCheckSeconds, lintSeconds, and totalControllerSeconds. Separate input reading, mapping, and lint times so mismatch stops can show whether lint was unexecuted. Each stack retains changeSetCreateSeconds, changeSetWaitSeconds, executionSeconds, pollCount, and pollApiCount. This is resume/measurement information outside the repository; do not save it in Git/models.

For initial deploy local preparation, `deploy_preparation.py` checks fixed Python dependencies together and uses authoritative stack readers/task reservation checks to generate external contract candidates, mandatory document chunks, and one controller argv. `--register` registers confirmed candidates using existing task_contract CLI; `--run-controller` starts only one controller containing all StackNames, once. Preparation does not duplicate AWS APIs, mappings, or lint; retain controller account, issue, mapping, lint, delete/replacement, and failure stops. Stop if references or new parts needed for observed synchronization are outside reserved scope; do not expand scope.

Record environment, contractPreparation, documentRead (I/O), documentReview (elapsed after snapshot until registration), and contractRegistration in external `timing.jsonl`. Ordinary preparation within 60 seconds is a measurement target, not a condition for omitting safety checks. Controllers with `--timing-log <external-file>` record total startup time, authenticationContext (STS/context), and awsApi (operation/service only), including failures/timeouts. Parallel API call durations are individual durations; do not interpret their sum as wall time. Do not save secrets or API arguments/responses in timing logs. Session metric contextCheckSeconds also retains authentication/context time. Record stops before session creation such as authentication failures in external logs; do not confuse them with preparation time.
